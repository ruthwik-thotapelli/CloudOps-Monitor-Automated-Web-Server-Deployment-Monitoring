PROJECT FOUNDATIONS

Automating the Cloud Delivery Lifecycle

Traditional web infrastructure suffers from manual configuration drift, unrecorded changes, and delayed incident awareness. CloudOps Monitor replaces manual administration with programmatic idempotency and proactive observability.

Declarative State Management

Infrastructure is codified using Puppet manifests (site.pp). Instead of executing manual bash scripts, administrators define what state the server must remain in, ensuring repeatable provisioning across fleets.

  • Deterministic package & service control
  • Manifest version control via Git
  • Idempotent runs without side effects

Automated Drift Correction

Accidental human modifications, unauthorized port shifts, or stopped daemons are automatically detected. During the periodic catalog run, Puppet reconciles variations back to the verified standard without human intervention.

  • Automatic remediation of stopped Nginx daemons
  • Protection against manual filesystem changes
  • Strict enforcement of file permissions (0644)

Continuous Health Observability

Integrated Nagios Core daemon conducts high-frequency polling on critical system layers: host ICMP ping, root disk utilization, RAM saturation, and true HTTP 200 OK socket availability.

  • Granular warning/critical threshold logic
  • Continuous HTTP content validation
  • Instant alert trigger on service disruptions

01

Provisioning & Manifest Execution

AWS EC2 virtual machines are initialized with baseline network rules and SSH keys. The Puppet agent periodically executes runs against the manifest, validating that the nginx package is installed, the service is enabled on boot, and document roots have strict permissions.

02

Continuous Health Checking

Nagios Core continuously polls the provisioned web server using active check plugins. The check_http plugin queries port 80, expecting a status code of HTTP 200 and verifying header response latency within predefined SLA thresholds.

03

Self-Healing & Verification

If an administrator accidentally terminates Nginx or alters server configurations, Nagios transitions the service to a CRITICAL state. Upon the next Puppet cycle, the agent re-starts Nginx and restores files, prompting Nagios to automatically resolve back to OK.

End-to-End Deployment & Recovery Workflow

Explore the multi-phase deployment pipeline from initial EC2 cloud provisioning to declarative convergence and continuous Nagios health verification.

PHASE 01: PROVISIONING

AWS EC2 Infrastructure Bootstrapping

The workflow starts with spinning up clean Ubuntu 22.04 LTS instances in an Amazon VPC. Security groups are configured with ingress rules for SSH (port 22) and HTTP (port 80), along with standard outbound egress.

  • AWS EC2 t2.micro or t3.small compute initialization
  • Elastic IP and VPC Security Group association
  • Secure SSH keypair authentication & base apt updates
bash • cloud-init.sh 
# Update package index and install Puppet
sudo apt-get update -y
sudo apt-get install -y wget curl gnupg2

# Configure Puppet 7 repository
wget https://apt.puppet.com/puppet7-release-jammy.deb
sudo dpkg -i puppet7-release-jammy.deb
sudo apt-get update -y
sudo apt-get install -y puppet-agent

# Verify Puppet agent binary
/opt/puppetlabs/bin/puppet --version
PHASE 02: AUTOMATION

Declarative Puppet Configuration

Rather than manually running apt install nginx, our configuration is codified in /etc/puppetlabs/code/environments/production/manifests/site.pp.

  • Package resource guarantees Nginx presence
  • File resource delivers the static portfolio assets
  • Service resource enforces running state & startup on boot
puppet • site.pp 
node 'webserver.cloudops.internal' {
  # Ensure Nginx package is installed
  package { 'nginx':
    ensure => 'installed',
  }

  # Ensure service is always active and enabled
  service { 'nginx':
    ensure    => 'running',
    enable    => true,
    require   => Package['nginx'],
  }

  # Deploy static website bundle
  file { '/var/www/html/index.html':
    ensure  => 'file',
    source  => 'puppet:///modules/web/index.html',
    mode    => '0644',
    notify  => Service['nginx'],
  }
}
PHASE 03: DRIFT DEFENSE

Continuous Configuration Drift Correction

When unauthorized staff tamper with the server (e.g. stopping Nginx, altering HTML files, or messing with permissions), Puppet detects the divergence during its periodic catalog execution and silently reverts to the declared golden image.

  • 30-minute automated cron enforcement cycle
  • Immediate state convergence without downtime
  • Audit logging of all resource modifications

PHASE 04: OBSERVABILITY

Nagios Core Health Polling

Nagios Core continuously probes the live web server across both network and operating system layers. Any breached threshold moves through SOFT retries to HARD alerts.

  • check_ping: Packets transmitted, RTT response latency
  • check_http: Validates HTTP 200 code & payload under 200ms
  • check_disk & CPU: Resource saturation triggers warnings
cfg • /usr/local/nagios/etc/objects/webserver.cfg 
define service {
    use                     generic-service
    host_name               webserver-ec2
    service_description     HTTP Web Availability
    check_command           check_http!-u / -p 80 -t 5
    check_interval          1
    retry_interval          1
    max_check_attempts      3
    notification_interval   30
}
PHASE 05: RESILIENCE

Simulated Failure & Automated Recovery

To validate the DevOps resilience loop for our viva demonstration, we deliberately induce an outage by shutting down the Nginx process: sudo systemctl stop nginx.

  • Nagios flags CRITICAL: Connection refused on port 80
  • Puppet agent kicks off catalog reconciliation
  • Nginx service is restarted automatically; Nagios returns to OK
bash • viva-demo-simulation.sh 
# Step 1: Deliberately break the service
$ sudo systemctl stop nginx

# Step 2: Nagios polls and detects outage
[12:04:12] CRITICAL - Connection refused (port 80)

# Step 3: Trigger Puppet agent reconciliation
$ sudo /opt/puppetlabs/bin/puppet agent -t
Notice: /Service[nginx]/ensure: ensure changed 'stopped' to 'running'

# Step 4: Nagios automatically returns to OK
[12:04:45] OK - HTTP/1.1 200 OK - 1.48 KB in 0.002s - 200 OK

ACADEMIC & ENGINEERING GOALS

Core Project Objectives & Achievements

Demonstrating how contemporary DevOps principles transform manual server management into an automated, auditable, and resilient production infrastructure.

01 PROJECT GOAL

Infrastructure Automation

Eliminate manual SSH provisioning commands. All server configuration (Nginx installation, systemd daemon management, static asset placement) is codified into reusable, version-controlled Puppet manifests.

100% Codified Provisioning
02 PROJECT GOAL

Configuration Consistency

Enforce idempotency across the computing environment. Regardless of whether a manifest executes once or hundreds of times, the resulting server state remains identical, completely eradicating snowflake servers.

Zero Configuration Drift
03 PROJECT GOAL

Availability Monitoring

Implement proactive observability using Nagios Core. Track end-to-end HTTP response codes, latency roundtrips, CPU load thresholds, and partition quotas with automatic notification triggers.

Active Health Polling
04 PROJECT GOAL

Resilience & Verification

Empirically verify disaster recovery and self-healing. When services are intentionally crashed or configuration files modified, Puppet actively repairs the defect, and Nagios validates immediate restoration.

Automated Remediation Loop
VIVA / PRESENTATION DEFENSE READY

Why Puppet & Nagios Over Manual Scripts?

Bash scripts lack idempotency and require complex error-handling conditions. Puppet provides a declared state engine that only modifies resources when variance exists. Coupled with Nagios Core's independent external watchdog, our architecture establishes an automated cycle of continuous deployment and proactive health verification.
